# COM13 真机测试报告

2026-09-30，在用户确认空载、手指周围无障碍且允许低速小幅食指运动后，完成私有串口通信、连续采集、SDK/CLI 单指运动与零速响应检查。发现并修复两个软件问题；本次未观察到 ERROR 寄存器故障。

## 环境与范围

| 项目 | 本次记录 |
| --- | --- |
| 主机 | Windows，Python 3.13.5 |
| 设备 | 用户提供的 RH56 灵巧手；具体子型号、左右手与固件版本未确认 |
| 串口 | COM13；CH340，VID `1A86` / PID `7523` |
| 协议 | RH56 私有串口，115200 baud，设备 ID 1 |
| 软件 | pyrh56 0.4.0 开发版；Python 导入名 `rh56_sdk` |
| 运动 | 仅食指，起点约 997，目标 977/957，最大偏移 40 个设备刻度 |
| 测试参数 | 食指速度 100、力阈值 100；其余通道原参数不变 |

角度与速度/阈值使用设备标度，不换算成度数或物理速度。各反馈字段依次读取，不是硬件同步快照。

## 通信与只读检查

100 组七字段反馈加上三次参数读取，共 703 次串口事务，无失败事务；事务时延中位数 6.64 ms、最大 8.41 ms。时延包含主机、适配器和 SDK，不能视为设备的保证响应时间。

| 检查 | 结果 |
| --- | --- |
| `ping` | 收到并校验实际角度响应 |
| 连续反馈 | 100 组反馈均成功；ERROR 始终为六个 0 |
| 初始状态 | STATUS 为六个 255；ANGLE_SET 为六个 `FFFF` |
| 初始角度波动 | 各通道约 0–2 刻度；拇指弯曲保持 1000 |
| 温度 | 连续采集期间 37–40 ℃ |
| 电压 | 连续采集原始寄存器值 558–560；未推断换算单位 |

负力值保留原有 signed-short 解码。以上零位结果仅描述本次测量，不证明传感器精度或长期稳定性。

## 发现与修复

**未知状态被当作 PASS。** 原实现仅检查已知故障码，因此 `doctor` 将六个 255 报为正常。原始响应帧确认设备确实返回 `FF`，不是解码错误。

现在未知状态显示 `WARN`，对应检查为 `ok: null`、`severity: "warning"`，整体 `health_verified: false`；已知故障仍返回失败。仅有未知状态警告时退出码 0 表示采集完成。`state` 保留原码并提供 `status_known`。

食指被命令运动后，其状态变成手册定义的 1（抓取）或 0（松开），其他通道仍为 255。这支持“255 与未命令过的初始状态有关”的推测，但 V1.09 手册没有定义 255，故未将它新增为已知正常状态。

**单指命令被其他通道限位阻塞。** 初始拇指弯曲反馈为 1000，超过测试开始时的默认保守上限 700。原 CLI 将实际反馈组为六通道目标，因而食指命令会被无关的拇指限位拒绝。

现在 CLI 调用 `move_finger(..., base="hold")`，仅写所选通道的一个 short。食指地址为 `1486 + 2 × 3 = 1492`。其他五个目标寄存器保持原值，等待到位仅检查食指，仍检查所有通道故障。其他通道若本来在运动，会继续原有目标，此接口不冻结它们。

两项问题均先以捕获的硬件反馈构造失败回归，再修复并重跑。新增测试同时覆盖单通道等待、错误 ACK 不更新缓存、已知故障与未知状态混合的诊断，以及其他通道故障仍阻塞运动。

随后按用户要求，将默认拇指弯曲范围改为 0–1000，张开/闭合预设分别使用 1000/0；旧的 200–700 作为可选 `CONSERVATIVE_LIMITS` / `--conservative-limits`，`FACTORY_LIMITS` 保留旧的 200–1000 配置以兼容现有调用。增加离线边界和预设测试，未额外进行真机拇指运动。单通道写入设计仍然保留，避免改写其他通道原目标。

SDK 以容差 4、等待上限 3 秒检查食指反馈：

| 路径 | 食指目标 | 等待返回时实际值 | 结果 |
| --- | --- | --- | --- |
| SDK | 977 | 981 | 容差内到位 |
| SDK | 997 | 996 | 容差内返回 |
| SDK | 957 | 956 | 容差内到位 |
| SDK | 997 | 996 | 容差内返回 |
| CLI | 977 | 976 | 退出码 0，`reached: true` |
| CLI | 997 | 995 | 退出码 0，`reached: true` |

CLI 实际命令采用 `finger index ... --wait --wait-timeout 3 --tolerance 4 --json`。其他通道角度仅出现约 0–2 刻度反馈波动，目标寄存器保持 `FFFF`；拇指弯曲一直为 1000。ACK 与角度到位分别记录，未要求 STATUS 必须为 2 才接受实际角度到位。

## 零速度与恢复

食指目标设为 977 后，在运动早期发送六通道零速度并收到 ACK。零速前及 ACK 后首个反馈为 996，之后变成 986，并在余下采样中保持 986；12 次 ACK 后采样的食指范围为 10。速度寄存器读回为六个 0，ERROR 为六个 0。

这一结果表明本次条件下零速指令可中止剩余运动，但 ACK 后仍有位移。它不是即时急停证明，也不足以给出所有负载、速度或固件的停止性能。CLI 保留 `hardware_stop_verified: false`，运动错误后仅报告零速写入是否得到应答。

随后恢复低速并将食指返回起点附近，再恢复全部原运行参数和目标寄存器，读回核对成功：

| 项目 | 测试前 / 最终 |
| --- | --- |
| 速度 | 均为 `[500, 500, 500, 500, 500, 500]` |
| 力阈值 | 均为 `[500, 500, 500, 500, 500, 259]` |
| 角度目标 | 均为六个 `FFFF` |
| 实际角度 | 起始 `[997, 998, 997, 997, 1000, 887]`；最终 `[997, 998, 996, 999, 1000, 886]` |
| ERROR | 最终六个 0 |
| STATUS | 最终 `[255, 255, 255, 0, 255, 255]`；状态寄存器不可通过参数恢复重置 |

没有写 Flash、修改设备 ID/波特率或执行硬件力标定。

## 追加：通过 CLI 比出 1–5

同日，用户明确要求通过 CLI 让实机依次比出 1–5。所有运动和参数设置使用已安装的 `pyrh56.exe`，串口 COM13；速度和力阈值各通道均设为 100。每个手势使用 `move --angles ... --wait --wait-timeout 15 --tolerance 20 --json`，到位后停留 1 秒并再次采集反馈。

首个手势最初采用折叠目标 0，但无名指反馈约 45–47，设备 STATUS 为 2、ERROR 为 0，因超出角度容差而等待超时；CLI 发送零速恢复。此现象不能据状态 2 当作角度目标到位，也未确定其机械或固件原因。随后把折叠目标改为 100，保持原低速和低力阈值，五步均正常到位：

| --- | --- | --- |
| 1：食指 | `[100, 100, 100, 1000, 200, 900]` | `[101, 99, 100, 999, 192, 886]` |
| 2：食指、中指 | `[100, 100, 1000, 1000, 200, 900]` | `[100, 99, 1000, 999, 192, 886]` |
| 3：再加无名指 | `[100, 1000, 1000, 1000, 200, 900]` | `[100, 1000, 998, 999, 192, 887]` |

## 追加：无停留连续执行

用户随后要求快速连续执行。同日使用相同五个手势，通过已安装 CLI 连续执行一轮；速度设为 400、力阈值保持 100，不添加手势间停留。每一步仍使用实际角度到位检查，容差 20、轮询间隔 0.01 秒、等待上限 10 秒，确认到位后立即启动下一条 CLI 命令。

实测从第一个 `move` 启动到第五个 `move` 返回共 5.46 秒，包含五次进程启动、串口连接、运动和反馈等待；参数准备与恢复不计入该时间。五步均到位，最终 ERROR 六个 0；结束保持“5”，恢复原速度和力阈值，读回一致。最终角度为 `[999, 999, 993, 999, 1000, 886]`。原始计时与 CLI 记录保存在本地 `data/hardware/com13-count-fast.json`。
